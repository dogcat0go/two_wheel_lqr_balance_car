# ROS 2 Runtime 实验流程（PC + 两块 ESP32）

> **这份文档的定位**：`ros2_runtime_perf_labs.md` 的执行版，只覆盖 runtime 架构与低延迟两条线。
> 选型理由、取舍依据、其余实验组都在原文档，这里只回答三件事：**做什么、记什么、什么算通过**。
>
> **设备**：x86 Ubuntu 主机（暂时顶替树莓派当上位机）、ESP32-A（雷达采集发布）、ESP32-B（电机 + 200 Hz 控制环）。
>
> **一句话前提**：主机上测出的**机制**可以搬到 ARM，**数值不能**。见原文档 §9.2。

---

## 0. 开工前：不做这步，后面全白测

这一节不是准备工作，是实验的一部分。**测量环境不受控，优化结论就不成立**——这句话本身在面试里就能讲。

### 0.1 固定环境

```bash
sudo cpupower frequency-set -g performance
sudo cpupower idle-set -D 0        # 禁深 C-state，去掉唤醒延迟的随机性
```

其余必须跨轮次保持一致的量：

| 变量 | 要求 |
| --- | --- |
| RMW 实现 | 固定 `RMW_IMPLEMENTATION`，全程不换。换了就是另一组实验 |
| 输入数据 | 同一个 rosbag，或同一个合成发生器 + 固定随机种子 |
| 可用核数 | 用 `taskset -c 0,1` 把整套进程压到 2 核。**这是改结构参数，不是造假负载**（区别见原文档 §9.3） |
| 后台负载 | 关掉浏览器、IDE、同步盘。`uptime` 的 1 分钟负载在开跑前应接近 0 |
| 时长 | 每轮 ≥ 5 min，**丢弃前 30 s**（预热、首次缺页、DDS 发现都在这段里） |
| 重复 | 每个配置跑 3 轮 |

最后一条最容易被跳过，但它决定结论成不成立：**如果轮间差异大于配置间差异，你测到的是噪声，不是效果**。先看这个，再看别的。

### 0.2 记录模板

每轮固定填这张表，缺一项后面就没法归因：

| 字段 | 取法 |
| --- | --- |
| 探针周期误差 p50 / p99 / max | 探针节点自己写 CSV（见 §1.1） |
| heavy 回调时长 p50 / p99 | `ros2_tracing`，或探针旁路计时 |
| 线程总数 | `ls /proc/<pid>/task \| wc -l`，多进程时求和 |
| 自愿 / 非自愿上下文切换 | `pidstat -w -p <pid> 1` |
| 调度延迟 max | `perf sched record -- sleep 20 && perf sched latency --sort max` |
| 总 CPU / RSS | `pidstat -u -r -p <pid> 1` |

> **`ros2_tracing` 是次要工具，不是主要工具。** 主指标一律由探针节点自己记时间戳落 CSV——零依赖、不会因为 LTTng 没装好而卡住。tracing 用来回答"时间花在哪个回调"，出问题时才需要。

## 1. 阶段一：主机内的 runtime 架构

**这一阶段不接任何硬件。** executor 抖动、回调排队、进程划分收益全部在主机单一时钟上测量，不需要跨设备时间同步（这条纠正见原文档 §9.3）。

### 1.1 被测系统：三个节点

| 节点 | 行为 | 角色 |
| --- | --- | --- |
| `scan_src` | 10 Hz 发一个 `LaserScan` 尺寸的消息（360 点） | 负载源。ESP32-A 接上后换成真数据，其余不动 |
| `heavy` | 订阅 `scan_src`，每帧占用约 50 ms | 重回调。后期换成真的 slam_toolbox |
| `probe` | 100 Hz 定时器，**什么也不做，只记录自己被调用的时刻** | **被测指标的载体** |

`probe` 是整套实验的核心，它只需要做一件事：在回调里取一次 `steady_clock`，攒够后落 CSV。

**主指标定义**（含糊的定义会让后面所有对比失效）：

```
周期误差(n) = 第 n 次回调实际进入时刻 − (t0 + n × 10 ms)
```

**记分布，不记平均。** `hz=100` 完全可以是 5 ms / 15 ms 交替跑出来的。

### 1.2 五种配置，每次只动一个变量

| 配置 | 进程 | Executor | 回调组 | intra-process | 相对上一行改了什么 |
| --- | --- | --- | --- | --- | --- |
| **C0** 基线 | 1 | Single | 全默认 | 关 | —— |
| **C1** | 1 | **Multi** | 全默认 | 关 | 只改 executor |
| **C2** | 1 | Multi | **heavy 独立 Reentrant** | 关 | 只改回调组 |
| **C3** | **3** | 各自 Single | —— | 关 | 只改进程划分 |
| **C4** | 1 | Multi | 同 C2 | **开** | 只改 intra-process |

一次只动一个变量是这套设计的全部意义。四个变量混在一起改，测出来的差异无法归因给任何一个。

### 1.3 预期结果，以及那个最值得记住的结论

| 对比 | 预期 | 说明 |
| --- | --- | --- |
| C0 | 探针 p99 被顶到 50 ms 以上 | **复现不出来就没有实验**，见下方判据 |
| C0 → C1 | **几乎没有改善** | ← 这是整套实验最值钱的一条 |
| C1 → C2 | 探针 p99 回落到接近 C0 的 p50 | 真正的解法在这里 |
| C2 → C3 | 尾延迟相近，但线程数与上下文切换明显上升 | 进程隔离的代价 |
| C3 → C4 | CPU 与 RSS 下降，尾延迟不劣化 | 组合 + 零拷贝的收益 |

**为什么 C0 → C1 几乎没用：** 所有回调默认落在同一个 `MutuallyExclusive` 回调组里，`MultiThreadedExecutor` 拿到再多线程也不能并行跑它们。**光换 executor 不配回调组，等于没换。**

这条值得单独拿出来讲，因为它是常见误解，而你有数据。原文档 §2.3 说的"能用数据推翻常见说法，比复述常见说法有价值"，指的就是这种。

### 1.4 判据

- **C0 必须先复现问题。** 探针 p99 应达到 heavy 回调时长的量级。没复现就调 heavy 的耗时或 `scan_src` 的频率，直到复现为止——基线不成立，后面四个配置都没有参照。
- 每个配置 3 轮的轮间离散必须**小于**配置之间的差异。否则回到 §0.1 查环境。
- 最终交付是一张五行表，外加一句结论：**这次收益主要来自哪一项**。如果数据显示主要是线程数和上下文切换的功劳而不是省了拷贝，照实写。

### 1.5 换成真负载

ESP32-A 接上后：`scan_src` 换成真雷达数据，`heavy` 换成真的 slam_toolbox。**五种配置和全部测量脚本一行不改。**

这一步做完，你手上就有了合成负载与真实负载的两组对照——机制是否一致、数值差多少，本身就是一个结论。

## 2. 阶段二：链路延迟

接入 ESP32。这一阶段的顺序是按"先摘纯收益，再做有权衡的"排的。

### 2.1 第一项：`microros_task` 里那个无条件的 10 ms

`CommHost.cpp` 的 micro-ROS 任务循环末尾有一句无条件的 `vTaskDelay(pdMS_TO_TICKS(10))`。它给每一条下行 `cmd_vel` 加了 0~10 ms 的固定延迟，**与网络无关，纯粹是任务结构造成的**。

排在最前面是因为它是**纯收益**，没有权衡要讨论，适合用来跑通整条测量链路。

- **测什么**：`cmd_vel` 从主机发出，到 ESP32 侧 `CommandInput.stamp_ms` 更新，这段时延的分布
- **怎么测**：跨设备单向时延需要时间同步，此处不需要——用**主机单钟的往返测量**：主机发指令、ESP32 在遥测里回显收到的序号、主机记 RTT
- **改法**：**别直接删**。删掉会让这个优先级 1 的任务空转吃满 Core0。正确做法是让它阻塞在数据上而不是阻塞在时钟上
- **判据**：p99 下降且 Core0 空闲率不恶化。**两个都要看**——只看延迟会得出"删掉最好"的错误结论

### 2.2 A2：大消息分片

现成的问题，不用注入：`custom_microros.meta` 里 MTU 是 1024，而 360 点的 `LaserScan` 光 `ranges` 就 1440 字节。一帧被切成 3~4 个 UDP 分片，best-effort 下**任何一片丢失，整帧作废**。

- **测什么**：帧级丢失率对点数的曲线（扫描点数从 180 加到 720）
- **拧哪些旋钮**：MTU、`RMW_UXRCE_STREAM_HISTORY_INPUT/OUTPUT`（当前是 4 槽）、socket 缓冲区
- **判据**：能画出"点数 → 丢帧率"的拐点，并说明拐点位置由哪个参数决定

### 2.3 A5：WiFi 尾延迟

不需要 `tc netem`，真实 WiFi 自带重传与退避。

- **测什么**：RTT 分布的尾部（p99、p999、max），跑够 30 min
- **注意**：它影响的是控制指令，**不影响建图质量**——原因见原文档 §2.1。能主动说清这一点，比测出数字更重要

### 2.4 C1：切到串口之后

把 `board_microros_transport` 改成串口之后：

- **必做的调优**：USB 转串口芯片的默认 latency timer 常常是 16 ms。不改的话，你刚从 WiFi 省下来的延迟会原样还回去
- **测什么**：改 latency timer、VMIN/VTIME 前后的时延分布；`strace -c` 看 syscall 次数放大
- **判据**：p99 显著低于 WiFi，且**方差大幅收窄**——串口的价值主要在确定性，不只在均值

### 2.5 这一阶段的产出

一句能讲的完整故事，正好套进原文档 §10 的模板：现象是 WiFi 下丢帧率多少、p99 多少；定位是 MTU 分片加 best-effort；修复是换串口；数据是前后对照表。

**"我为什么把无线换成有线"比"我会配 QoS"有分量得多。**

## 3. 阶段三：调度与实时

### 3.1 B5：PREEMPT_RT 前后对比

x86 上没有版本冲突，22.04 与 24.04 都能装 generic 变体：

```bash
sudo pro enable realtime-kernel
uname -v | grep -q PREEMPT_RT && echo "RT 已启用"
```

- **测什么**：`cyclictest` 在装 RT 内核前后的对比，加载与不加载背景负载各一组
- **判据**：max 延迟量级下降。**注意 cyclictest 测的是内核调度，不是你的 ROS 节点**——两者都要测，且要能说清区别

### 3.2 B3：实时优先级与核隔离

- `SCHED_FIFO` + `mlockall`，`isolcpus` / `nohz_full`，中断亲和
- **判据**：探针周期的 max 下降；同时记录代价——被隔离的核不能再跑别的

## 4. 时间同步：理论部分

> 按要求这里只写原理，不写接线与实现。实现在 `docs/esp32_time_sync.md`。

### 4.1 为什么需要它，需要多准

先算清楚需求，否则容易过度设计。误差主要来自**旋转**而非平移：

| 运动 | 时间戳误差 10 ms 造成的配准误差 |
| --- | --- |
| 平移 0.5 m/s | 5 mm |
| **旋转 1 rad/s** | **0.57°，在 3 m 处是 3 cm 横向误差** |

结论：目标定在**差分误差 < 1 ms**。

注意是**差分**。SLAM 做的是 scan 与 odom 的配准，它在乎的是"这两帧数据是不是同一时刻的"，不在乎它们相对 UTC 差多少。**共同偏移无害，相对偏移致命。**

这个结论直接决定了架构：精度只需要建立在两块 MCU 之间，上位机的时钟只要一个粗估计即可。

### 4.2 双向时间传递，以及它的软肋

NTP 与 PTP 的核心算法是同一个，都是四时间戳交换：

```
NTP：  θ      = ((t2 − t1) + (t3 − t4)) / 2
PTP：  offset = ((t2 − t1) − (t4 − t3)) / 2
```

展开后是同一个式子。那个**除以 2 就是全部软肋——它假设往返路径对称**。任何不对称都会原样变成偏移误差，大小是不对称量的一半。PTP 规范里绝大部分复杂度（Follow_Up、透明时钟、边界时钟、非对称补偿）都是在补这一个洞。

所以「PTP 比 NTP 准」不是因为算法更好，算法完全一样。差别在三处：**时间戳打在哪一层**（用户态 vs MAC/PHY 硬件）、**中间设备是否参与**（透明时钟把交换机内的滞留时间显式减掉）、**对网络的假设**（NTP 假设网络恶劣，PTP 假设网络受控）。

最有力的佐证：**NTP 配一个 PPS 参考钟就能到 µs 级**。同一套算法，只是加了一根脉冲线，精度提升三个数量级。**协议不是瓶颈，时间戳的物理位置才是。**

### 4.3 专线脉冲为什么能绕开

一根 30 cm 导线上的传播延迟约 1~2 ns，而且它是**已知常数，不是待估量**。没有往返，就没有对称性假设，那一整套补偿机制都不需要。

这在结构上不是"PTP 的替代品"，而是 **PPS**：**专线负责精度，报文负责身份**。GPS 接收机用 PPS 边沿给出精确时刻、用 NMEA 报文说明这是哪一秒；这里用脉冲边沿给出精确时刻、用遥测里的序号说明这是哪一个脉冲。

工程上 PPS 与 PTP 通常是配合的：授时服务器从 GPS 的 PPS 建立本地精度，再用 PTP 分发到全网。不同层次，不是竞争关系。

### 4.4 必须同时估 offset 和 skew

两个晶振不仅起点不同，**走速也不同**。只估偏移不估频率比，误差会随时间线性发散。

典型晶振漂移 10~40 ppm。按 40 ppm 算是 40 µs/s——**同步一次之后放十分钟，偏差约 24 ms**，已经是 §4.1 目标的 24 倍。

所以模型必须是两参数的：

```
t_B = t_A + offset + skew × (t_A − t_ref)
```

用滑动窗最小二乘拟合。数值上有个坑：时间戳绝对值很大，直接回归会病态，**拟合前必须先中心化**。

### 4.5 三个常见误区

| 误区 | 为什么错 |
| --- | --- |
| 用 `message_filters` 的 `ApproximateTimeSynchronizer` 当时钟同步 | 它做的是**消息配对**，假设时间戳已在同一时间轴上。时钟差 10 ms，它照样把实际差 10 ms 的两帧配成一对，**而且不报错**。静默错误比崩溃难查得多 |
| 在上位机按收到的时刻重新打戳 | 传输延迟可变，到达时刻不是采样时刻的好代理。这等于把链路抖动直接注入时间轴 |
| 只做一次 `rmw_uros_sync_session()` | 见 §4.4，skew 会让它十分钟后失效。而且它把每块 MCU 各自同步到 agent，**A 与 B 的差分误差是两次独立误差之和，不会抵消** |

### 4.6 分层结论

| 层 | 用什么 | 精度 |
| --- | --- | --- |
| 粗对齐（确定"这是哪一个脉冲"） | `rmw_uros_sync_session()`，micro-ROS 自带，不用自己写 | ±10 ms 量级，够用 |
| 精度层（差分对齐） | GPIO 专线脉冲 + 上位机拟合 | 几十 µs |

两者不是二选一，是分层。1 Hz 脉冲的歧义窗口是 ±500 ms，粗对齐只要好于这个数，配对就是唯一无歧义的。

### 4.7 一个反直觉的优势

因为原始本地时间戳全部保留、映射在上位机做，**可以用后来的数据重新拟合早期的点**。离线处理 rosbag 时能跑非因果的双向平滑，精度严格优于任何实时伺服——PTP 的伺服环是因果的，做不到这件事。

## 5. 每个实验做完就填

```
【现象】   什么条件下、什么指标、坏到什么程度（带数字）
【假设】   当时怀疑的 2~3 个方向，以及为什么先查这个
【定位】   用了什么工具、看到什么关键证据
           —— 关键是说清「这个证据如何排除了另外两个假设」
【修复】   改了什么，为什么这么改，代价是什么
【数据】   前 / 后：p50、p99、max、丢帧率、CPU、内存
【边界】   这个修复在什么情况下会失效
```

最后一栏最容易被跳过，**而面试官最爱追问的就是它**。能主动说出"这个优化在跨机场景下不成立"或"这个数在 ARM 上要重测"，说明是在做工程，不是在抄配置。
