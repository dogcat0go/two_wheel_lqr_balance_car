ROS2 运控向：分层、实时卫生、DDS 与 ros2_control

岗位要的不是「会的 ROS2 特性数量」，而是：平衡回路为什么不进 DDS、QoS 怎么按数据选、rclcpp 回调里为什么不能 new、以及 ros2_control 三层和你 MCU 固件怎么一一对应。本讲针对双轮足陪伴机器人（Orin + 实时板），不是通用入门课。

你已经有：话题 / 服务 / 参数 / Launch、Nav2 部署、slam_toolbox、micro-ROS 联调。短板不在广度，在 C++ 侧实时纪律 和 能对照 ros2_control 讲自己的分层。

1. 先钉死：ROS2 站在哪一层

双轮足户外陪伴机器人的典型拆分：GPU 板跑感知和策略，实时板跑估计与关节力矩。ROS2 / DDS 在 GPU 板的进程间；板间是 CAN / 串口帧，不是 topic。

Jetson Orin（Linux ARM）
  相机 / 检测 / 跟随          ─ 30 Hz，可丢
  RL 推理（ONNX/TensorRT）    ─ 50 Hz 量级，可超时
  Nav2 / SLAM                 ─ 输出 /cmd_vel，可停
  运动编排节点（rclcpp）      ─ 读状态、仲裁 writer、下发指令
           │  二进制帧  seq + t + CRC + timeout
           ▼
实时板（FreeRTOS / 你现在的 ESP32）
  200 Hz read → 估计 → LQR/安全 → write
  硬故障自己锁存；软故障只清 v*,ω*
           │  CAN 力矩
           ▼
FOC 驱动器 / 轮毂 + 髋膝

图 1 · ROS2 停在编排层。回路内一旦出现 WiFi/DDS 不确定延迟，倒立摆的相位账会立刻穿仓。

你已经用真机做过这个决策：不稳定极点约 \(15\,\mathrm{rad/s}\)，平衡环下沉 MCU，ROS2 只做指令与遥测；指令超时只清速度、保持本地站立。本讲后面所有 API 都服务于这句话，而不是把 200 Hz 搬进节点定时器。

和仿真车仓库的关系

Gazebo 里 balance_controller_node（Python，200 Hz 墙钟）是仿真里的 MCU 扮演者。真机上同等代码在 control_task。面试不要说「我用 ROS2 做了 200 Hz 控制」——要说「仿真为了方便把扮演 MCU 的环写在节点里；实车证明这条环不能走 DDS」。

2. 图模型压缩复习（只记运控用得到的）

原语运控里干什么别用它干什么
Topic 状态流、cmd_vel、关节命令、心跳 不要用 topic 当 RPC；不要假设每条都到
Service 切模式、clearFault、标定触发（低频） 不要在 200 Hz 回调里同步 call()
Action Nav2 导航目标；可取消、有反馈 不要用 Action 下发力矩
Parameter K、限幅、超时阈值；可动态改 改参不要在实时路径里锁住参数服务
Launch / Composition 确定性拉起；多节点进同一进程减拷贝 Launch 不是实时调度器

和 ROS1 的关键差别（面试 20 秒）：没有 roscore。发现靠 DDS；节点可以后上线；QoS 成为一等公民；rclcpp 与 rclpy 共用同一套中间件。产品上通常锁死一个 RMW（Fast DDS 或 Cyclone），而不是现场混用。

3. QoS：五要素、兼容性、场景表（要能讲）

五要素够用（Humble 面试按这个说）：

  1. Reliability：BEST_EFFORT（可丢） / RELIABLE（重传直到成功或超时）
  2. Durability：VOLATILE（后订阅看不到历史） / TRANSIENT_LOCAL（发布方缓存，后上线也能拿到最后若干条）
  3. History：KEEP_LAST(n) / KEEP_ALL
  4. Deadline：期望的最大消息间隔（可配合事件回调做超时）
  5. Liveliness：对端还活着吗（LEASE 到期 = 心跳丢了）

3.1 兼容性：订阅不能严于发布

DDS 的 offered/requested：发布方提供一组 QoS，订阅方请求一组。请求更严则匹配失败、安静地收不到数据——这是联调里最阴的一类 bug。

项能连不能连
Reliability BE 订 REL 发；REL 订 REL 发；BE 订 BE 发 REL 订 BE 发
Durability VOL 订 TL 发；同档互订 TL 订 VOL 发（后上线指望历史，发布方却没存）
History 深度 订方 depth ≤ 发方（KEEP_LAST 时）通常能匹配 订方要的历史比发方缓存更多

默认值会坑运控

rclcpp 话题默认往往是 RELIABLE + VOLATILE + KEEP_LAST(10)。高频 IMU / 关节状态用可靠重传，会在 WiFi 差时把延迟堆积进队列。传感器流应显式 BEST_EFFORT + KEEP_LAST(1)：只要最新一帧。

3.2 场景选型（背这张表）

数据ReliabilityDurabilityHistory理由
IMU / 关节状态 / 遥测 BEST_EFFORT VOLATILE KEEP_LAST(1) 过期帧有害；丢了等下一拍
/cmd_vel、策略 action BEST_EFFORT 或 RELIABLE 短队列 VOLATILE KEEP_LAST(1) 要最新指令；用 stamp + 超时兜底，不靠重传
地图、全局路径 RELIABLE TRANSIENT_LOCAL KEEP_LAST(1) 后启动的规划器必须拿到图
TF（动态） BEST_EFFORT VOLATILE KEEP_LAST 适当 tf2 自带缓存；静态 TF 用 static broadcaster
故障锁存、模式（若走话题） RELIABLE TRANSIENT_LOCAL KEEP_LAST(1) 后上线调试器要看到当前模式；仍要 MCU 终裁

超时不要只靠 QoS Deadline。你固件里用 cmd.stamp_ms 判 kCmdTimeout 更硬：应用层超时在 MCU，中间件超时只是辅助。

4. DDS：RMW、发现、户外、零拷贝

ROS2 的中间件是可替换的 RMW。Humble 常见：rmw_fastrtps_cpp（Fast DDS，默认）、rmw_cyclonedds_cpp。环境变量 RMW_IMPLEMENTATION 切换。产品上选定一个、全员一致；混用会在发现和 QoS 边角上出鬼。

4.1 发现（Discovery）

没有 master。默认参与者用组播互找。实验室局域网没事；户外陪伴机器人用 WiFi 热点 / 拥挤 2.4 GHz 时，发现流量和假节点会把链路打满。

  • 默认 SPDP 组播：节点上下线都在喊，机器一多就吵。
  • Discovery Server（Fast DDS）：指定一台当发现服务器，其它只连它。适合「Orin 为中心、偶尔一台调试笔电」。
  • 静态发现 / 白名单：量产镜像里写死对端 GUID，现场不再自动爬网。

面试一句话：控制链路不走「任意设备自动发现的 DDS」；板间本来就不是 DDS。Orin 内部进程用 DDS 时，把发现范围锁在本机或本机+调试口。

4.2 进程内零拷贝

同一进程里多个节点（component composition + use_intra_process_comms:=true）可以借指针传递，避免序列化。适合 Orin 上「相机驱动 → 跟踪 → 编排」同进程。跨板、跨机器仍要拷贝和序列化，别指望零拷贝救 WiFi。

和你内核网络经历的接法

发现、组播、QoS 重传都是网络问题。你做过协议栈和软总线，可以说：DDS 把可靠性和发现做成了中间件策略，运控要做的是别让这些策略进入力矩闭环，而不是再实现一遍 DDS。

5. TF2 与时间（要能默画）

5.1 为什么拆 map → odom → base_link

map ——(定位，可跳变，长期无漂)——► odom ——(轮式积分，连续，会漂)——► base_link
       定位节点发                         运控 / diff_drive 发

图 2 · 两段互斥需求：控制要平滑，地图要无漂移。拆开才能两者都要。

  • odom → base_link：由运控或 diff_drive_controller 发。积分轮速 / IMU。控制、局部规划只信这一段的连续性。
  • map → odom：由 SLAM / 定位发。它改的是「里程计坐标系在地图里哪」，不直接改 base_link，避免控制环看到姿态跳变。
  • 静态外参（base_link → imu_link / camera）：static_transform_broadcaster 或 URDF。

你在差速车上已经配过这棵树。轮足多一个「腿长变化」：髋相对轮心的高度会变，要用关节状态或单独 TF 更新，不能把 \(h\) 写死在 URDF 里当常值（那是滑轨/第一版仿真可以偷懒的地方）。

5.2 时间

  • use_sim_time:=true：节点跟 /clock。Gazebo 卡了，定时器一起变慢。你仿真车用 use_sim_time:=false 是为了墙钟 200 Hz；真机 MCU 更是自己的晶振。
  • 消息 stamp 用「数据产生时刻」不是「发布时刻」。视觉 30 Hz、控制 200 Hz：编排层取最新一帧并检查年龄，过期当软故障。
  • 互补滤波你用名义周期 \(dt\) 而不是时钟差——和 ros2_control 把 period 传入 update() 是同一纪律：估计器不要吃抖动的时间戳。

6. Executor 与 CallbackGroup（要能讲死锁）

rclcpp 把回调丢给 Executor 调度。默认 SingleThreadedExecutor：同一时刻只跑一个回调。MultiThreadedExecutor 才能并行，但必须给回调分组。

含义运控含义
MutuallyExclusive 组内回调不同时跑 保护无锁假设下的共享状态
Reentrant 组内可重入 只有回调可重入时才用

6.1 死锁标准场景（要能口述）

SingleThreadedExecutor
  定时器回调 on_timer()
      └─ client->call(clear_fault)   // 同步等响应
           └─ 需要同一 executor 去跑 service 响应回调
                └─ 执行器正被 on_timer 占着
                     →  永久等待

图 3 · 回调内同步 service = 自己等自己。

改法（记两条就够）：

  1. 异步 async_send_request，不要在实时回调里阻塞；
  2. 或者把 service 回调放到另一个回调组 + MultiThreadedExecutor。

你在 ESP32 上用双核 + 共享内存快照，就是在硬件上做了「通信回调不准进控制核」。rclcpp 里对应：控制定时器一个组，服务/订阅另一个组，跨组只拷 POD。

7. 生命周期：确定性启动，不是装饰

无生命周期节点：main 里构造完就 publish，订阅方可能还没起来，硬件可能还没 claim。Lifecycle 把节点变成状态机：

Unconfigured → Inactive → Active，外加 Finalized。Nav2 的 lifecycle_manager 按 yaml 顺序切状态，就是为了「地图先好、定位再好、规划最后」。ros2_control 的 controller inactive / active 也是生命周期：active 才允许 claim 命令接口。

运控编排节点值得做成 lifecycle：configure 打开 CAN/串口并核对 Schema 版本；activate 才允许 writeCommand；deactivate 先发安全指令再松接口。

8. ROS2 不是硬实时：把相位账算完（要手推）

硬实时：每拍截止时间必须满足，超时视为故障。Linux + DDS 默认不是。PREEMPT_RT + 隔离核 + 无锁可以「尽量实时」，仍不是 MCU 上 vTaskDelayUntil 那种保证。

相位滞后（弧度）\(\varphi = \omega \Delta t\)，换成度：

$$ \varphi(^\circ) = \omega\,\Delta t \cdot \frac{180}{\pi} \approx 57.3\,\omega\,\Delta t. $$

用你车上不稳定极点 \(\omega \approx 15.2\,\mathrm{rad/s}\)：

\(\Delta t\)来源\(\varphi\)
1 ms尚可的板间周期抖动\(0.87^\circ\)
5 ms同机 DDS / 一次调度延迟\(4.4^\circ\)
20 msWiFi + 重传，很常见\(17.4^\circ\)

你已算过：该构型相位裕度上限约 \(11.6^\circ\)，数字实现自己已经吃掉约 \(19.7^\circ\)。再塞 5–20 ms 的 DDS，不是「差一点」，是账已经为负还继续借。所以：

  • 回路（站立、关节电流）在 MCU；
  • ROS2 只发参考（\(v^*,\omega^*,L^*,\) 模式），超时 MCU 自己降级；
  • 仿真 Python 200 Hz 节点是教具，不是架构目标。

和名义周期同一纪律

AHRS 用 kCtrlDt 而不是 micros() 差；ros2_control 的 update(time, period) 里 period 由 manager 传入。两者都拒绝把时钟抖动喂进离散滤波器。

9. rclcpp 实时卫生（真缺口，要能写能讲）

JD 满篇 Modern C++。你现有控制节点是 Python。补的不是「再学一套 API」，是把 MCU 上已经遵守的纪律搬到 Orin 编排节点：

纪律MCU 上你怎么做的rclcpp 上对应
固定周期 vTaskDelayUntil 200 Hz create_wall_timer；真正闭环仍在板端
跨核只拷 POD ControlSnapshot + portMUX realtime_tools::RealtimeBuffer / lock-free 队列
实时路径无分配 定长数组、无 printf 回调里禁止 new、日志、字符串拼接、vector 扩容
命令超时 kCmdTimeout 清速度 看 stamp；过期不写力矩，通知 MCU 保持站立

订阅回调（非实时线程）只把最新指令塞进 RealtimeBuffer；定时器 / 板端周期任务取出来用。这就是 diff_drive_controller 里 rt_command_ptr_ 的做法。

// 示意：订阅线程写，周期任务读。不要当完整节点抄进工程。
#include <realtime_tools/realtime_buffer.hpp>

struct Cmd { float v{0}, w{0}; rclcpp::Time stamp; };

realtime_tools::RealtimeBuffer<Cmd> rt_cmd;

void on_cmd(const geometry_msgs::msg::Twist::SharedPtr msg) {
  Cmd c;
  c.v = msg->linear.x;
  c.w = msg->angular.z;
  c.stamp = now();          // 非实时侧可以分配
  rt_cmd.writeFromNonRT(c);
}

void on_cycle() {           // 周期侧：无锁读、无 new
  Cmd c = *rt_cmd.readFromRT();
  if ((now() - c.stamp).seconds() > 0.2) { c.v = c.w = 0; }
  send_to_mcu(c);           // 预分配的帧缓冲
}

Composition：把编排、遥测、策略适配器 load 进同一 component_container，本机热路径少一次序列化。策略推理（GPU）往往仍是独立进程，用心跳 + stamp 连过来——挂了不拖垮编排器。

绑核、优先级、mlockall 属于 Linux 实时调优，知道「Orin 上编排节点可以隔离到非 GPU 核」即可；平衡环仍然不靠这一层保证。

10. ros2_control：三层、claim、对照你的固件

JD 写了 ROS2 / DDS，没点名 ros2_control。它是 Linux 上把「硬件抽象 + 周期调度 + 控制律插件」标准化的那一套。你不必在项目里用过，但必须能对照着讲。

10.1 三层

controller          控制律插件（PID、差速、LQR…）
        │  claim 某几个 command interface
        ▼
controller_manager  固定周期：read → update → write
                    生命周期 + 资源占用表
        │
        ▼
hardware_interface  read() 采样 / write() 下发
                    声明 state / command 接口名

图 4 · 和 MCU 主循环同构，只是跑在 Linux 上。

ros2_control你的固件仿真 Python 节点
hardware_interface::read/write WheelSensor / WheelActuator 订 /joint_states、发 /wheel_effort_controller/commands
manager 的 read→update→write control_task 200 Hz on_timer
controller 插件 BalanceController + LQR LqrBackend / CascadePidBackend
command interface 互斥 claim 同一拍只有一套 \(\tau\) writer 启动时二选一（尚未热切）
joint_state_broadcaster 只读状态上报，不占执行器 debug 话题

10.2 Claim 与切换

同一个 joint1/effort 不能被两个 active controller 同时 claim。切换：先 deactivate 旧的（释放），再 activate 新的。 switch_controllers --deactivate A --activate B 是原子切换，避免中间一拍无人写力矩。

joint_state_broadcaster 只读 state interface，所以不冲突——和「遥测任务不写 PWM」同一逻辑。

10.3 update() 里的四条（读 diff_drive 时只盯这些）

  1. period 由 manager 传入，自己不要用墙钟差当 \(dt\)。
  2. 命令来自 RealtimeBuffer，无锁。
  3. cmd_vel_timeout 过期则速度清零——对应你的软故障。
  4. 无 new、无锁、无打印。

面试标准立场

「架构我清楚，项目里没用过官方插件。MCU 上手写了等价结构。平衡回路放 Linux+DDS 过不了相位账；ros2_control 更适合仿真侧或上层关节伺服。产品模式切换是策略 writer 与 LQR writer 的仲裁，不完全等于 switch_controllers。」

11. 「模式切换」其实是三件不同的事

是什么和岗位你怎么证明
A. 算法插件 Balance 模式下 PID / LQR / MPC 换实现 框架要能挂多种控制器，通常启动时选定 仿真 backend 接口；不要写成产品热切
B. ros2_control claim 同一 command 接口互斥、原子切换 资源管理机制，可类比 能讲 + 跑过 demo 即可
C. 产品运行模式 Stand / Balance(LQR) / RLWalk / Fault；RL 心跳丢了 writer 回到 LQR JD 要的模式切换 真机：硬故障锁存、软故障不断平衡

C 的硬规则你已经在车上实现过一半：

  • 单 writer：balancing 时只有 LQR 写 \(\tau\)；
  • 软故障不改模式：kCmdTimeout 只清 \(v^*,\omega^*\)；
  • 硬故障改模式并锁存：摔倒 / IMU 丢失，要 r 才武装。

缺的是把「策略进程」显式当成可超时的 writer（RLWalk）。PID↔LQR 热切只练 B，不能当作 C 写上简历。

  • Nav2 挂了：/cmd_vel 停，MCU 清速度、继续站。你仿真里 cmd_vel_timeout_sec 已经是这个语义。

13. 闭卷自测

0 / 0.5 / 1 分。建议 🔴 全满再去跑 ros2_control demo。

Q1 · 为什么 200 Hz 平衡不能走 ROS2 topic？请用相位数字。
\(\varphi=57.3\,\omega\Delta t\)。\(\omega\approx15.2\) 时 20 ms WiFi 约 \(17^\circ\)，超过该构型约 \(11.6^\circ\) 的相位裕度上限，且数字实现已经把账花负。故回路在 MCU，ROS2 只发参考。
Q2 · RELIABLE 订阅 + BEST_EFFORT 发布，会怎样？运控传感器该怎么选？
匹配失败，安静无数据。传感器：BEST_EFFORT + KEEP_LAST(1)。控制指令靠 stamp 超时，不靠重传堆延迟。
Q3 · 地图为什么用 TRANSIENT_LOCAL？cmd_vel 为什么不用？
后启动节点必须拿到图。cmd_vel 只要最新；存历史会把过期速度当新命令。
Q4 · 口述一个 rclcpp 死锁，以及两种改法。
单线程执行器里，定时器同步 service call，响应回调无法被调度。改：异步请求；或 service 换回调组 + 多线程执行器。
Q5 · map→odom 和 odom→base_link 各谁发、为什么拆？
定位发前一段（可跳、无漂）；运控发后一段（连续、会漂）。控制要平滑，地图要全局一致，一段 TF 做不到。
Q6 · ros2_control 三层各干什么？joint_state_broadcaster 为何不占接口？
硬件 read/write + 声明接口；manager 周期与 claim；controller 是控制律。broadcaster 只读 state，不 claim command。
Q7 · 同一关节两个 controller 同时 active？正确切换姿势？
不能，command interface 互斥。先 deactivate 再 activate；用 switch_controllers 做原子切换。
Q8 · 产品模式切换、PID↔LQR、switch_controllers 各是哪一层？
产品：谁写 \(\tau\)（RL vs LQR）+ 故障态。PID/LQR：同一 Balance 模式的插件。switch_controllers：Linux 侧接口占用机制，可类比单 writer，不是 RL 退化本身。
Q9 · update() 为什么不能 new / printf？你的固件对应物？
不确定延迟、锁、缺页。对应 control_task 定长运算；跨核用快照+自旋锁，不用队列阻塞。
Q10 · 视觉丢帧该进 Fault 吗？
不应。软故障：清跟随速度，LQR 继续站。Fault 留给摔倒、IMU、驱动器、急停。
