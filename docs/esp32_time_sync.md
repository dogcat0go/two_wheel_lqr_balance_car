# 两块 ESP32 的硬件时间同步

> 上下文与精度推导见 [`ros2_runtime_perf_labs.md` §2.2](ros2_runtime_perf_labs.md)。
> 结论回顾：**硬要求只有一条——ESP32-A（雷达）与 ESP32-B（电机/IMU）之间的差分误差 < 1 ms**。两者到 ROS 时间的共同偏移是无害的，软件估计即可。

本文是这一条硬要求的落地设计。

---

## 1. 三个架构决策

### 1.1 MCU 之间只走脉冲，不走数据

两块 ESP32 之间**只连一根信号线 + 一根地线**，不建立数据链路。所有配对与拟合都放在上位机做。

理由：

- 两块 MCU 本来就各自和上位机通信，再加一条 MCU 间数据链路是多余的复杂度；
- 拟合算法要调参、要看残差、要处理异常，**放在上位机可以随便改，不用反复烧固件**；
- 固件侧的职责被压缩到极简：一个记录发出时刻、一个记录捕获时刻，各自随遥测上报。

### 1.2 ESP32-B 当主机

它已经有最稳的时基和最规整的定时任务（200 Hz `vTaskDelayUntil`），从既有循环里每 200 拍翻一次电平就是 1 Hz 脉冲，几乎零成本。

### 1.3 脉冲规不规整，其实无所谓

这一点反直觉但很重要：**脉冲不需要精确周期，甚至不需要周期。** 它只是一个"两边都能看到的共同事件"。主机晚发 50 µs 没有任何影响，因为主机记录的是**实际发出时刻**。

真正要保证的只有一件事：**两边测量同一个物理边沿的时刻，各自都要准。** 脉冲什么时候来，不重要。

想清楚这一点之后，实现难度大幅下降——不需要 LEDC、不需要 MCPWM、不需要额外定时器。

---

## 2. 硬件连接

```
ESP32-B ──[GPIO 输出]──┬── 330Ω ──► [GPIO 输入] ESP32-A
                       │
                    (共地线) ──────────────────────
```

三个必须注意的点：

1. **必须共地。** 两块板若各自供电又没有共地，这根信号线的电平没有参考，轻则误触发重则烧口。这是最容易漏、后果最严重的一条。
2. **串一个 330 Ω 限流电阻**，防止上电时序不同导致的灌流。两边都是 3.3 V，不需要电平转换。
3. **防电机噪声。** 线要远离电机和驱动器走线，必要时加 RC 低通或用屏蔽线。软件侧也要防：**拒绝间隔明显不等于 1 s 的边沿**，把毛刺挡在拟合之外。

---

## 3. 固件侧：两段都很短

### 3.1 ESP32-B（主机）：发脉冲并记录发出时刻

挂在既有的 200 Hz 控制循环里，每 200 拍一次：

- **先写 GPIO，再立刻读 `esp_timer_get_time()`**。顺序不能反——GPIO 寄存器写入几乎立即生效，紧跟着读时间，误差在亚微秒。
- **这两步要放进临界区**（`portENTER_CRITICAL`），否则中间插进一个中断就会引入几微秒的虚假延迟。
- 维护一个自增的 `pulse_seq`，和时间戳一起存进环形缓冲。

用 `esp_timer_get_time()` 而不是 `micros()`：前者是 64 位微秒，不会像 32 位的 `micros()` 那样约 71 分钟回绕。做长跑统计时这很关键。

### 3.2 ESP32-A（从机）：捕获边沿

- `attachInterrupt(pin, handler, RISING)`，中断服务函数里读 `esp_timer_get_time()` 存环形缓冲。
- **ISR 必须加 `IRAM_ATTR`。** 否则 flash 操作期间 ISR 要等 cache miss，会被拖延几十微秒——这是 ESP32 上很经典的坑，而且它的影响正好和我们的误差预算同量级。
- 中断注册在**不跑 WiFi 的那个核**上，避免和 WiFi/lwIP 抢。
- 维护自增的 `capture_seq`。

精度这样就够了（ISR 延迟 1~2 µs）。ESP32-S3 的 MCPWM capture 或 ETM 能做到亚微秒的纯硬件锁存，但按第 5 节的预算，**没有必要**——先做简单版，测出来不够再升级。

### 3.3 各自上报什么

随现有遥测上传最近几个脉冲记录即可（1 Hz 的数据量可以忽略）：

| 字段 | 说明 |
| --- | --- |
| `boot_id` | **每次上电随机生成一次。** 上位机靠它发现 MCU 重启过，立即作废旧的拟合结果 |
| `pulse_seq` / `capture_seq` | 自增序号，用于发现丢失的边沿 |
| `t_local_us` | 该边沿的本地 `esp_timer_get_time()` |

多带几条历史记录（比如最近 4 条），这样偶尔丢一包遥测不会丢同步点。

## 4. 上位机侧：配对、拟合、换算

### 4.1 配对

两侧序号各自独立，需要对齐。稳妥做法：

1. 先用一次软件握手（NTP 式四时间戳交换）拿到 **±10 ms 量级**的粗偏移；
2. 1 Hz 的脉冲间隔是 1 s，粗偏移远小于 ±500 ms，所以**配对是唯一的、无歧义的**；
3. 配好之后做一致性校验：相邻配对的残差应当连续，突然跳变说明丢了边沿，丢弃该点。

> 这就是选 1 Hz 而不是 10 Hz 的原因：10 Hz 收敛快一点，但歧义窗口只有 ±50 ms，配错一个就是 100 ms 的灾难性错误。等 1 Hz 跑稳、配对逻辑验证过了，再考虑提速。

### 4.2 拟合

模型是两个时钟的线性关系：

```
t_B = t_A + offset + skew · (t_A − t_ref)
```

`skew` 是两块晶振的相对频率差，ppm 量级；`offset` 是常数偏移。

**必须注意的数值陷阱：** `esp_timer_get_time()` 的值很大（跑一小时就是 3.6e9 µs）。直接拿这种量级的 x 去拟合一条斜率接近 1 的直线，`float` 精度会被吃光，算出来全是噪声。

正确做法是**先中心化，再拟合残差**：

```
x_i = t_A,i − t_A,0                      // 相对第一个点
y_i = (t_B,i − t_B,0) − x_i              // 只拟合「漂移量」，是个小数
y ≈ skew · x                             // 数值条件良好
```

用**滑动窗口最小二乘**（60 个点，即 1 分钟）比带遗忘因子的 RLS 更容易调对，也更容易看懂。测量噪声不到 1 µs，在 60 s 跨度上估斜率，理论精度约 0.02 ppm，收敛很快。

### 4.3 换算

把 A 的所有数据时间戳换算到 B 的时间轴，再整体映射到 ROS 时间。第二步的绝对精度不敏感，但**必须平滑单调**——时间戳倒退会让 TF 和 SLAM 直接报错，所以映射要做限速，不能因为重新拟合就跳变。

## 5. 误差预算

| 环节 | 量级 | 说明 |
| --- | --- | --- |
| B 侧记录自身边沿 | < 1 µs | 临界区内写 GPIO 后立即读时钟 |
| A 侧 ISR 捕获 | 1~2 µs | `IRAM_ATTR` 是前提；否则可能几十 µs |
| 脉冲之间的晶振漂移 | < 20 µs | 1 Hz × ±20 ppm；已被 skew 估计吃掉大部分 |
| 拟合残差 | 几 µs | |
| **合计** | **几十 µs** | **对 1 ms 目标有 20 倍以上余量** |

余量这么大是故意的：温度变化会让晶振频率漂移，实车上的裕度要留够。

---

## 6. 怎么验证（关键：要用独立的基准）

拿同步用的那根脉冲去验证同步精度是循环论证。要另找一个**两边都能看到、且与同步脉冲无关**的事件：

- 再拉一根线，由**上位机**产生**随机间隔**的测试脉冲，A 和 B 同时捕获；
- 两边各自记录本地时刻，按已建立的映射换算到同一时间轴；
- 两个数的差就是**真实的差分同步误差**。

上位机用户态翻转 GPIO 的抖动在这里完全不影响——因为它是同一个边沿同时到达两块板。

三项验收：

| 项 | 判据 |
| --- | --- |
| 差分误差 | 独立测试脉冲测得的差值，p99 < 100 µs |
| 长跑稳定性 | 连续 30 min，skew 估计收敛到稳定 ppm 值，残差不发散 |
| 温度鲁棒性 | 冷启动到热平衡的过程中误差不超预算（这决定滑动窗口能开多大） |

---

## 7. 失效处理

同步一旦坏掉必须**被发现**，不能静默地继续输出错误时间戳——这和驱动的失效语义是同一个道理。

| 故障 | 检测 | 处理 |
| --- | --- | --- |
| 信号线断 / 松动 | 超过 N 秒没有新的捕获 | 标记降级，发 `/diagnostics`，退回软件同步 |
| 丢边沿 | 序号跳变，或残差突跳 | 丢弃该点，不污染拟合 |
| MCU 重启 | `boot_id` 变化 | **立即作废整个拟合**，重新采集。这是最容易漏掉的一条——不处理的话，重启后的时间戳会被旧模型换算成完全错误的值 |
| 电机噪声误触发 | 边沿间隔不接近 1 s | 直接丢弃 |

---

## 8. 分步实施

不要一次做完，每步有独立判据：

1. **接线 + 两边各自打印边沿时刻。** 判据：A 侧每秒稳定收到一个边沿，间隔抖动 < 100 µs。这一步就能暴露共地、噪声、`IRAM_ATTR` 三个问题。
2. **上位机收集配对并离线拟合。** 判据：残差图是白噪声、无系统性弯曲，skew 是个稳定的 ppm 数。
3. **接上独立测试脉冲验证。** 判据：差分误差 p99 < 100 µs。
4. **接进数据链路**，把 A 的时间戳换算过去。判据：原地旋转建图，墙面不再重影。
5. **补失效处理**（第 7 节）。判据：拔掉信号线、重启任一 MCU，系统都能正确报降级并恢复。

## 9. 与 PTP（IEEE 1588）的关系

### 9.1 本质差别：估计延迟 vs 消除延迟

PTP 的核心难题是**"这条消息从主走到从用了多久"**。它靠 Sync / Delay_Req 四个时间戳去**估计**这个延迟：

```
offset = ((t2 − t1) − (t4 − t3)) / 2
```

那个除以 2 就是整个协议的软肋——**它假设往返路径对称**。任何不对称都会原样变成偏移误差（大小是不对称量的一半）。PTP 规范里绝大部分复杂度（Follow_Up 消息、透明时钟、边界时钟、非对称补偿）都是在对付这一个问题。

专线脉冲把这个问题从根上删掉了：一根 30 cm 导线上的传播延迟约 1~2 ns，而且它是**已知常数**，不是待估量。没有往返，就没有对称性假设，也就不需要那一整套机制。

### 9.2 处理时钟的方式：驯服 vs 换算

| | PTP | 本方案 |
| --- | --- | --- |
| 对从时钟做什么 | 用伺服环（PI）调整其频率与相位，让它**成为**主时钟 | **不碰任何时钟**，只在上位机维护一个映射函数 |
| 软件怎么用 | 读系统时钟就自动是同步时间，对应用透明 | 需要显式换算 |
| 副作用 | 要改系统时钟，涉及跳变与单调性；伺服要调参 | 无 |
| MCU 可行性 | ESP32 的 `esp_timer` 无法调频，只能软件补偿 | 天然适配 |
| **能否回溯修正** | **不能**，伺服是因果的 | **能**。原始本地时间戳都留着，可以用后来的数据重新拟合早期的点 |

最后一行是被低估的优势：离线处理 rosbag 时可以用**非因果的双向平滑**重新换算，精度严格优于任何实时伺服。

### 9.3 精度来源不同

PTP 的精度天花板由**时间戳打在哪一层**决定：软件时间戳（内核 socket 层）几十 µs 到 ms；硬件时间戳（MAC/PHY 层）亚 µs 到 ns。

本方案的精度由**边沿捕获抖动**决定：ISR 捕获 1~2 µs，硬件捕获 < 1 µs。

也就是说，**这套简单方案的精度接近 PTP 硬件时间戳的水平，远好于 PTP 软件时间戳**。而在 WiFi 上跑 PTP 是最差的组合——没有硬件时间戳，且 CSMA/CA 退避与重传会造成严重的往返不对称，正好踩中 §9.1 那个软肋。

### 9.4 其实这不是"PTP 的替代"，而是 PPS

本方案在结构上和 GPS 授时里的 **PPS（每秒脉冲）** 完全一致：**专线负责精度，报文负责身份**。GPS 接收机用 PPS 边沿给出精确时刻、用串口 NMEA 报文说明"这是哪一秒"；我们用脉冲边沿给出精确时刻、用遥测里的 `pulse_seq` / `boot_id` 说明"这是哪一个脉冲"。

PPS 和 PTP 在工程上通常是**配合**而非竞争：授时服务器从 GPS 拿 PPS 建立本地精度，再用 PTP 把时间分发到全网。两者处在不同层次。

### 9.5 什么时候该反过来选 PTP

| 条件 | 选什么 |
| --- | --- |
| 节点少、物理相邻、能拉线 | **专线脉冲**（本项目） |
| 节点多、需要选主与故障切换 | PTP（BMCA 是它的强项） |
| 跨越不可控的网络、拉不了线 | PTP |
| 需要与他厂设备互操作（车载、工业） | PTP（它是标准，这条往往压倒技术因素） |
| 需要可溯源的绝对时间（UTC/TAI） | PTP 或 GPS 授时 |

对本项目：**ESP32 之间用专线脉冲**；如果以后上位机变成两台（比如加一台做视觉），**那两台之间才轮到 PTP**——有线以太网、可能有硬件时间戳，用 `ptp4l` + `phc2sys`。先用 `ethtool -T <iface>` 查网口支持到哪一档，再决定能达到什么精度。两者不是二选一，是不同层次各管一段。

## 10. 一个容易被忽略的相邻问题

同步做完之后，`t_A` 是**「ESP32-A 收到雷达数据的时刻」**，不是**「雷达实际测量的时刻」**。两者之间隔着串口传输和驱动缓冲，是一段几到几十毫秒的固定延迟（见 [runtime 文档 C1](ros2_runtime_perf_labs.md)：FTDI 的 `latency_timer` 默认就有 16 ms）。

这段延迟是**常数偏置**，不会被时钟同步消掉，需要单独标定后从时间戳里减掉。方法：让车原地匀速旋转，扫描同一面墙，调整这个偏置值直到地图重影消失——**用建图质量本身当标定判据**。

同理，雷达一圈扫 100 ms，每条光束的时刻不同，`time_increment` 要填对并做去畸变。时间同步做到几十微秒、却在这里丢掉几十毫秒，是很常见的功亏一篑。
